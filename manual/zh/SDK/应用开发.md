## 安装包与运行环境

安装包包含 C++ 头文件与动态库、Python 绑定、示例程序和视频运行依赖。本手册推荐使用以下开发环境。

| 开发机系统 | 推荐 Python 解释器 | C++ 接口 |
| --- | --- | --- |
| Ubuntu 22.04 LTS x86_64 | CPython 3.10.x | C++17 |
| Ubuntu 24.04 LTS x86_64 | CPython 3.12.x | C++17 |

其他 Linux x86_64 环境需满足安装包 `BUILD-MANIFEST.json` 中记录的最低运行库符号要求，兼容性以实际验证为准。

Python 解释器由开发机环境提供，其次版本及架构必须与包内实际提供的绑定匹配，具体以安装包清单为准；虚拟环境同样适用。仅使用 C++ 时无需 Python。

将安装包完整解压到独立目录，保留目录结构。安装包携带 GStreamer 运行库和所需视频插件，无需额外安装系统 GStreamer；NVIDIA 驱动不随包提供，要求见[视频环境准备](#%E8%A7%86%E9%A2%91%E7%8E%AF%E5%A2%83%E5%87%86%E5%A4%87)。

| 目录或文件 | 用途 |
| --- | --- |
| `include/north_sdk/` | C++ 公共头文件 |
| `lib/` | SDK 及配套运行库 |
| `lib/python/` | 与目标 Python 版本匹配的绑定 |
| `lib/video-runtime/` | 随包视频运行库、插件及工具 |
| `bin/` | C++ 入门与连接诊断程序 |
| `examples/python/` | Python 示例与环境检查脚本 |
| `manual/` | 用户手册 |
| `setup.bash` | 加载当前包的库、Python 模块和视频插件路径 |
| `BUILD-MANIFEST.json` | 构建信息、Python ABI 和依赖清单 |

更新 SDK 时替换完整安装包，重新加载环境，并重新验证导入、只读连接和状态接收。

## 快速开始

本节目标是在不发送运动、模式、标定或供电命令的前提下，用最少步骤完成机器人连接和第一路状态接收。

> **安全说明：** 第一次连接只运行本节的只读程序。不要调用 `send_*()`、`set_mode()`、`enable()`、`reset()`、标定或 Power 管理接口。

### 1. 连接机器人

将开发机连接到机器人背部右侧交换机引出的以太网口，接通机器人电源并等待机器人软件启动。状态通信和时间同步均使用此有线连接。

默认机器人 IP 为 `192.168.100.100`，SDK 通过 UDP 端口 `7449` 通信。直连时，可在 Ubuntu 的“设置 → 网络 → 有线 → IPv4”中选择“手动”，例如将开发机设为 `192.168.100.10`、子网掩码设为 `255.255.255.0`，网关和 DNS 留空。确认该地址未被其他设备使用；现场修改过网段时，按实际地址配置。

### 2. 设置 SDK 和机器人地址

将下面的安装目录替换为实际解压路径。默认机器人地址可直接使用；现场地址如有变更再调整。

```bash
export NORTHSDK_PREFIX=/absolute/path/to/north-sdk
export NORTHSDK_ENDPOINT=udp/192.168.100.100:7449
source "$NORTHSDK_PREFIX/setup.bash"
```

环境变量只对当前终端及其启动的程序生效；新终端需重新设置。

`NORTHSDK_PREFIX` 指向解压后的 SDK 根目录，其中包含 `setup.bash`。

首次使用自动对时时，在普通开发账号的终端执行一次主机准备：

```bash
sudo "$NORTHSDK_PREFIX/tools/setup-host" --user "$USER"
"$NORTHSDK_PREFIX/tools/setup-host" check
```

该命令安装主机对时组件并授权当前账号。后续程序无需 `sudo`；更新 SDK 时用新包重新执行。软件对时可能使系统时间跳变，并临时暂停系统授时服务；最后一个对时会话关闭后恢复原服务状态。关闭对时的方法见[时间同步](#%E6%97%B6%E9%97%B4%E5%90%8C%E6%AD%A5)。

### 3. 运行只读诊断

```bash
"$NORTHSDK_PREFIX/bin/north_sdk_robot_smoke" \
  --endpoint "$NORTHSDK_ENDPOINT" --seconds 5
```

基础连接正常时，最后一行输出：

```text
PASS
```

`PASS` 表示已收到 Master 状态、硬件健康和至少一路心跳。按实际配置逐项检查所需设备流，`silent` 表示该流未收到样本。

### 4. 接收左臂状态

```bash
"$NORTHSDK_PREFIX/bin/north_sdk_quickstart" "$NORTHSDK_ENDPOINT"
```

左臂在线并持续发布时会看到类似输出：

```text
left arm seq=1234 joints=7
```

按 Ctrl+C 退出。如果机器人没有配置左臂，以 `robot_smoke` 中实际安装设备的数据流为准。

### Python 用户

先运行 `python3 --version`，确认解释器次版本与包内绑定匹配。Ubuntu 22.04 推荐 CPython 3.10.x，Ubuntu 24.04 推荐 CPython 3.12.x；虚拟环境也须使用包内支持的解释器次版本。

步骤 2 已设置 Python 模块路径，直接运行示例：

```bash
python3 "$NORTHSDK_PREFIX/examples/python/quickstart.py" \
  --endpoint "$NORTHSDK_ENDPOINT"
```

### 编译 C++ 示例（可选）

预编译程序运行成功后，如果需要验证 C++ 开发环境，可使用一条 `g++` 命令：

```bash
g++ -std=c++17 "$NORTHSDK_PREFIX/examples/cpp/quickstart.cpp" \
  -I"$NORTHSDK_PREFIX/include" -L"$NORTHSDK_PREFIX/lib" -lnorth_sdk \
  -Wl,-rpath,"$NORTHSDK_PREFIX/lib" \
  -o north_sdk_quickstart

./north_sdk_quickstart "$NORTHSDK_ENDPOINT"
```

`-L` 用于链接时查找库，`-Wl,-rpath` 记录 SDK 库目录；运行前仍需加载 `setup.bash`，以使用随包视频运行库和插件。安装目录迁移后应重新编译或更新运行时库路径。

### 完成标准

满足以下条件即可认为只读入门完成：

- `robot_smoke` 输出 `PASS`；
- 需要使用的设备流持续收到样本；
- C++ 或 Python 示例可以正常退出；

完成后继续阅读本章的订阅和运动控制说明，按任务选择[例程参考](%E4%BE%8B%E7%A8%8B%E5%8F%82%E8%80%83.md)。首次连接失败时，查看下面的[首次运行排查](#%E9%A6%96%E6%AC%A1%E8%BF%90%E8%A1%8C%E6%8E%92%E6%9F%A5)。

### 首次运行排查

首次连接、启动或 Python 导入失败时，按安装包、动态库和网络依次排查。以下检查沿用步骤 2 的环境变量，只在出现问题时执行。

#### 安装包或版本

```bash
test -f "$NORTHSDK_PREFIX/include/north_sdk/NorthSDK.h"
test -f "$NORTHSDK_PREFIX/lib/libnorth_sdk.so"
cat "$NORTHSDK_PREFIX/Version"
```

Python 导入检查：

```bash
python3 -c "import north_sdk; print(north_sdk.NorthSDK.version())"
```

若提示 `No module named 'north_sdk._north_sdk'`，先检查扩展是否存在及 Python 版本是否匹配：

```bash
python3 --version
ls "$NORTHSDK_PREFIX"/lib/python/north_sdk/_north_sdk*.so
```

检查安装包清单和 `lib/python/north_sdk/` 中实际提供的扩展。文件名中的 `cpython-312` 表示需要 CPython 3.12。解释器不匹配时切换到对应版本，或获取包含所需绑定的安装包；清单中列出的扩展缺失时重新获取完整包。

#### 动态库

```bash
ldd "$NORTHSDK_PREFIX/bin/north_sdk_quickstart" | \
  grep -E 'north_sdk|zenoh|protobuf|not found'
```

North SDK、Zenoh 和 Protobuf 应来自同一安装包。若出现 `not found` 或指向其他 SDK/ROS 环境，先修正 `LD_LIBRARY_PATH`。

#### 网络

```bash
ip route get 192.168.100.100
```

将 IP 替换为机器人实际地址，确认路由使用预期网卡。现场允许 ICMP 时可再执行 `ping`；Ping 失败不一定表示 Zenoh 不可用，最终以 `robot_smoke` 为准。

## 时间同步

SDK 默认在建立通信连接后准备 gPTP 对时。首次使用前完成[主机准备](#2-%E8%AE%BE%E7%BD%AE-sdk-%E5%92%8C%E6%9C%BA%E5%99%A8%E4%BA%BA%E5%9C%B0%E5%9D%80)。

| 选项 | 用法 |
| --- | --- |
| 软件模式（默认） | 调整开发机系统时间，网卡需支持软件收发时间戳。 |
| 硬件模式 | 创建 SDK 前将 `config.time_sync.mode` 设为 `TimeSyncMode::kHardware`（C++）或 `TimeSyncMode.HARDWARE`（Python）。需支持硬件时间戳和 PHC 的网卡，只调整网卡时钟。 |
| 关闭对时 | 创建 SDK 前设置 `config.time_sync.enabled = false`（C++）或 `False`（Python）。 |

运行以下命令检查对时：

```bash
python3 "$NORTHSDK_PREFIX/examples/python/time_sync_status.py" \
  --endpoint "$NORTHSDK_ENDPOINT" --mode software --seconds 10
```

输出中的 `state` 为 `READY` 且有 `robot_time_ns` 时，可通过 `sdk.robot_time_ns()` 读取同步时间。机器人使用 gPTP 时间域，不保证与 UTC 相同。

对时失败时，`connect()` 默认返回错误但保留通信连接；用 `time_sync_diagnostics()` 查看原因。需要继续使用连接时，按上述脚本处理错误。运行中失锁后，依赖同步时间的计算应等待重新就绪。

只验证通信时，可给 `north_sdk_robot_smoke` 添加 `--no-time-sync`。完整配置和诊断字段见[时间同步参数](%E8%BD%AF%E4%BB%B6%E6%9C%8D%E5%8A%A1%E6%8E%A5%E5%8F%A3.md#%E6%97%B6%E9%97%B4%E5%90%8C%E6%AD%A5%E5%8F%82%E6%95%B0)。

## 视频环境准备

需要使用视频时完成本节。先按“快速开始”加载安装包环境；GStreamer 运行库、解析/转换/JPEG 插件、NVIDIA 解码插件及精简 H.264/H.265 软件解码依赖均随包提供，无需安装系统 GStreamer。

### NVIDIA 驱动与随包运行库

默认使用 NVIDIA NVDEC 硬解，要求独显支持相机使用的 H.264/H.265 编码规格，并安装与 GPU 和 Ubuntu 版本匹配的 NVIDIA 驱动及解码运行库。驱动需单独安装。

先检查驱动：

```bash
nvidia-smi -L
```

无法列出 GPU 时，按 [Ubuntu 官方驱动安装说明](https://ubuntu.com/server/docs/nvidia-drivers-installation/)安装或修复驱动。NVDEC 使用驱动配套的 `libcuda.so.1` 和 `libnvcuvid.so.1`。GPU 对输入编码规格的支持可查询 [NVIDIA 官方解码支持表](https://developer.nvidia.com/video-encode-decode-support-matrix)。

`setup.bash` 设置 SDK 视频运行库、插件和缓存路径。新终端或应用启动环境中都要加载此脚本，视频程序使用当前 SDK 提供的运行库和插件。如果应用已加载其他 GStreamer 运行库，将视频接收放在独立进程中。

随包的软件解码用于兼容性和功能调试；没有 NVIDIA GPU 时可显式选择软件后端，不需要驱动。软件解码性能较差，多路或高分辨率场景可能严重降帧并增加时延，不建议用于实时任务；SDK 不会从硬解自动回退到软解。

### 检查视频环境

在运行视频示例的同一终端执行，默认检查 NVIDIA 硬解：

```bash
python3 "$NORTHSDK_PREFIX/examples/python/check_video_env.py" --backend nvdec
```

脚本检查本机 SDK 加载、GStreamer、视频插件及 GPU/驱动依赖，C++ 用户也可运行。每项 `OK` 且最终 `PASS` 表示依赖检查通过，再通过接收视频验证解码。出现 `FAIL` 时检查当前包环境、库和插件是否完整，以及驱动是否正常。

检查软件解码环境时，给脚本传入 `--backend software`。采集或预览程序的解码后端需分别指定，见下一步及[例程参考](%E4%BE%8B%E7%A8%8B%E5%8F%82%E8%80%83.md#%E8%AE%A2%E9%98%85%E5%A4%B4%E9%83%A8-jpeg)。

### 接收第一路视频

依赖检查通过且机器人头部左目在线后，运行单路只读采集，持续 5 秒且不保存图片：

```bash
"$NORTHSDK_PREFIX/bin/north_sdk_video_jpeg" \
  "$NORTHSDK_ENDPOINT" --no-save 0 85 --seconds=5 --nvdec
```

`0` 选择头部左目，`85` 为 JPEG 质量。结束时检查 JPEG 数量大于 0、无订阅或解码错误；没有 JPEG 时检查相机发布、网络及解码条件。需要软件解码时将 `--nvdec` 改为 `--software`，并先通过对应的环境检查。

需要浏览器预览时，使用[例程参考](%E4%BE%8B%E7%A8%8B%E5%8F%82%E8%80%83.md#%E8%AE%A2%E9%98%85%E5%A4%B4%E9%83%A8-jpeg)中的预览脚本；接口参数、视频来源和诊断字段见 [VideoClient](%E8%BD%AF%E4%BB%B6%E6%9C%8D%E5%8A%A1%E6%8E%A5%E5%8F%A3.md#videoclient)。

## 订阅和缓存

保存 `on_*()` 返回的 Subscription，句柄析构或 `close()` 会取消订阅。C++ 回调参数为借用引用，需要在回调后使用的数据应复制。回调保持短小，将耗时计算和阻塞操作交给应用自己的工作线程。

`latest_*(max_age)` 返回本地缓存副本，最大年龄从本机接收样本时计算。首次调用可能尚无数据，也可能返回 `kStaleState`；应等待新样本。

| 回调策略 | 用途 |
| --- | --- |
| `kDropOldest` | 默认；队列满时丢弃最老的可丢回调 |
| `kLatestOnly` | 合并同一订阅的待执行样本，适合状态显示 |
| `kReliable` | 本地不主动丢弃，队满施加背压 |

![首次无数据、有效缓存与缓存过期的时序](../../assets/zh/SDK/%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91/cache-timeline.svg)

图中以 `max_age=500 ms` 为例，250 ms 与 700 ms 表示样本的本机接收年龄。`latest_*` 会建立所需的状态接收，不要求先调用 `on_*`；如另行订阅 `on_*`，还会收到对应回调。

## 服务结果

先检查 SDK 调用结果，再检查机器人服务响应中的业务结果；持续运行时订阅心跳和错误事件。C++ 使用 `Result<T>` / `Status`，Python 捕获 `NorthSDKError`；具体字段和处理方式见[错误与结果检查](%E8%BD%AF%E4%BB%B6%E6%9C%8D%E5%8A%A1%E6%8E%A5%E5%8F%A3.md#%E9%94%99%E8%AF%AF%E4%B8%8E%E7%BB%93%E6%9E%9C%E6%A3%80%E6%9F%A5)。

## 运动控制

> **实机运动不是首次连接测试。** SDK 的本地校验和 Master 门禁不能替代硬件急停、机型限位、现场风险评估或机器人端安全控制器。

发送第一条运动命令前，至少完成以下检查：

- 急停装置已验证且操作员可立即触达，机器人周围已清场并按机型要求固定或支撑；
- 已取得当前机型的关节名称、数组顺序、正方向、零位、软硬限位及建议速度/加速度；
- 先读取新鲜反馈，按机型限位从当前位置生成小幅目标；
- 已确认任务 ID、CommandChannel、Master mode、设备使能和控制模式的组合由机器人交付配置支持；
- 控制循环在反馈过期、状态退出 RUNNING、SDK 错误或业务拒绝时立即停止继续发送；
- 已准备经审核的停止任务、急停及故障恢复步骤，并由现场监护人员确认可以开始。

机器人端的保护行为、限位数值和插值参数见[运动保护与轨迹处理](#%E8%BF%90%E5%8A%A8%E4%BF%9D%E6%8A%A4%E4%B8%8E%E8%BD%A8%E8%BF%B9%E5%A4%84%E7%90%86)。

运动命令要求 Master 状态新鲜且为 RUNNING。通道与运行模式的对应关系如下，准备顺序见[任务准备与结束](#%E4%BB%BB%E5%8A%A1%E5%87%86%E5%A4%87%E4%B8%8E%E7%BB%93%E6%9D%9F)。

| 通道 | Master 模式 |
| --- | --- |
| `kTeleoperation` | `kTeleoperation` |
| `kInference` | `kInference` |
| `kAutomation` | `kAutomation` |
| `kUniversal` | 任意模式，仍要求新鲜 RUNNING |

每侧臂为 7、每侧手为 22、躯干为 8 个关节，位置单位为 rad，数组按固定设备顺序填写。`JointCommand` 只填写完整 `position`；`name`、`velocity` 和 `torque` 保持为空。发送成功表示命令提交成功，动作是否完成应通过新鲜设备反馈判断。

![命令提交成功与设备动作完成的区别](../../assets/zh/SDK/%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91/motion-sequence.svg)

图示为单臂位置命令的调用顺序。运行条件不满足或目标参数无效时，SDK 返回错误。`kUniversal` 通道不检查模式匹配，但仍要求新鲜 RUNNING。

### 任务准备与结束

以下以 `inference` 任务发送位置目标为例。

1. **配置通道。** 创建 SDK 前设置 `config.command_channel = north::CommandChannel::kInference`（C++）或 `config.command_channel = CommandChannel.INFERENCE`（Python）。WholeBody 在每次 `send()` 时传入通道。

2. **确认空闲。** 读取新鲜 Master 状态，确认 `STANDBY`，检查所需设备健康，并确认其他控制端已停止发送命令。已有任务运行时，先按该任务的结束流程处理。

3. **准备设备。** 调用 `master().set_mode()`，传入 `OperationMode::kInference` / `OperationMode.INFERENCE`。待控制臂选择 `ControlMode::kJointPosition` / `ControlMode.JOINT_POSITION` 并调用 `enable()`；躯干选择 `TorsoControlMode::kPosition` / `TorsoControlMode.POSITION` 并使能；手选择 `HandMode::kPosition` / `HandMode.POSITION`。逐项检查服务结果和设备反馈。

4. **启动任务。** 调用 `master().start_task("inference")`，检查 `MasterResult`，再等待状态流同时满足 `RUNNING`、`Inference` 和 `task_id == "inference"`。健康检查失败时先处理设备问题。

5. **发送目标。** 从新鲜位置反馈生成完整、小幅且连续的目标。发送期间持续检查任务 ID、Master 阶段/模式及设备反馈；目标数组顺序见下节。

6. **正常结束。** 停止控制循环；底盘先持续发送零速度并通过反馈确认停稳。调用 `master().stop_task()`，检查业务结果，等待状态离开 RUNNING、确认设备反馈后关闭 SDK。反馈或通信故障时使用现场停止流程。

`start_task(task_id)` 接收区分大小写的任务 ID。标准配置中的客户任务如下，可用项以交付配置为准；未配置的 ID 会被拒绝。

| 任务 ID | 用途 |
| --- | --- |
| `inference` | 推理控制任务，本节使用的任务。 |
| `teleoperation` | 遥操作任务，使用独立的遥操作准备流程。 |
| `home` | 回位任务，会主动产生运动。 |
| `docking` | 对接任务。 |

`teleoperation` 正常结束时会执行回位，并在回位和录制收尾结束后退出 RUNNING。**停止遥操作任务可能继续产生运动，不能用作急停。**

退出系统急停时，`master().exit_estop()` 会启动设备复位和重新使能流程，包括双臂、躯干及手部模式恢复。调用前清空运动命令并确认现场允许恢复；服务成功响应表示流程已开始。等待 Master 离开 ESTOP，再检查健康、控制模式和新鲜位置反馈后启动新的控制循环。

### 关节数组与坐标

状态的 `joints.name[i]` 和 `joints.position[i]` 对应同一轴；命令也使用该固定下标，但发送时 `name` 留空。先打印当前设备完整状态，再与当前机型关节表核对。

| 部位 | 数组下标 | 状态名称 | 对应关系 |
| --- | --- | --- | --- |
| 每侧臂 | 0–6 | `joint_0`–`joint_6` | J1–J7；左右侧由 `Side` 选择。 |
| 躯干 | 0–4 | `torso_0`–`torso_4` | 身体 J1–J5，其中 J3/J4 为腰部俯仰/侧倾关节。 |
| 颈部 | 5–7 | `torso_5`–`torso_7` | 颈部 J6–J8，与身体一起组成完整 8 项命令。 |
| 每侧手 | 0–21 | `joint_0`–`joint_21` | 22 个关节。 |

位置单位为 rad。各侧关节的零位、转轴正方向及手指关节分组按交付机型的关节定义使用。

## 运动保护与轨迹处理

机器人对运动目标执行跳变检查、限位和插值处理。表中关节从 1 开始编号，SDK 数组从 0 开始索引。

### 命令准入与异常保护

臂和躯干根据**新目标与上一有效目标的差值**处理连续位置命令：差值在直接接收阈值内且未处于追赶或恢复过程时，接收整帧；超过该阈值时限制推进量；超过 Hold 阈值时拒收整帧。符合下述新鲜反馈条件的轴可免于触发 Hold。

| 部位与检查空间 | 直接接收阈值 | Hold 阈值 | 追赶速率 |
| --- | --- | --- | --- |
| 每侧臂，J1–J7 关节角 | 各轴 0.1745 rad | J1–J4：0.3491 rad；J5–J7：0.5236 rad | J1–J7：2.0944、2.0944、3.1416、3.1416、6.2832、6.2832、6.2832 rad/s |
| 躯干，8 个电机轴，按 ID 1–8 排列 | 0.0349、0.0349、0.0698、0.0698、0.0698、0.0873、0.0873、0.0873 rad | 0.1047、0.1047、0.2094、0.2094、0.2094、0.2618、0.2618、0.2618 rad | 1.0472、1.0472、1.0472、1.0472、1.0472、1.5708、1.5708、1.5708 rad/s |

追赶时，所有轴按最严格轴的比例缩小增量，时间额度不超过 20 ms。追赶速率用于追赶和恢复阶段。

反馈年龄不超过 50 ms、且目标与反馈差值在直接接收阈值内时，该轴可免于因相对旧目标的大跳变触发 Hold；位置命令仍受追赶约束。Hold 后须让各检查轴回到直接接收阈值内或接近上述新鲜反馈，才能恢复。**Hold 保留上一有效目标，机构可能继续已有运动。** 躯干阈值按电机轴计算。

机器人还会检查实际反馈与硬件状态：

| 保护 | 默认参数及行为 |
| --- | --- |
| 臂位置反馈越界 | 超过本节位置范围再向外扩展 0.0262 rad的边界时触发保护；应用目标仍使用表中的位置范围。 |
| 臂位置跟踪误差 | 位置安全检查启用时，目标与反馈差超过 J1–J4 的 0.3491 rad、J5–J7 的 0.6982 rad 时触发故障保护。 |
| 臂电机反馈与硬件故障 | 反馈为非有限值、驱动故障或电机速度超过电机 1–3 的 8.3776 rad/s、电机 4–7 的 26.7035 rad/s 时触发故障保护。 |
| 底盘命令超时 | 100 ms 未收到有效运动命令后退出当前速度命令；是否停稳以速度反馈为准。 |

发生故障后检查心跳错误和服务响应，再按恢复流程处理。默认未启用自碰撞检查，应用需规划避障。

### 连续位置命令的平滑处理

臂和躯干使用五次插值，将连续位置目标转换为高频控制目标。应用持续发送平滑目标。

| 参数 | 每侧臂 | 躯干 |
| --- | --- | --- |
| 控制周期 | 1 ms（1000 Hz） | 2 ms（500 Hz） |
| 名义命令周期 | 20 ms | 20 ms |
| 插值速度参数 | 10 rad/s | 1.0472 rad/s（电机空间） |
| 插值加速度参数 | 30 rad/s² | 2.0944 rad/s²（电机空间） |

名义周期用于插值参考，允许发送间隔波动。目标变化较大时，执行时间可能延长。插值参数、追赶速率和关节限速分别作用于不同阶段；应用负责规划速度、加速度和 jerk。

机器人用五次多项式连接一段运动的起点与终点，同时衔接两端的位置、速度和加速度：

```text
q(t) = a0 + a1 t + a2 t² + a3 t³ + a4 t⁴ + a5 t⁵,  0 ≤ t ≤ T
```

其中 `q` 为位置（rad），`T` 为本段时间（s）；六个系数由段首、段末的位置、速度和加速度确定。连续目标到来时，从当前运动状态衔接下一段。

![位置目标与平滑控制目标](../../assets/zh/SDK/%E5%BA%94%E7%94%A8%E5%BC%80%E5%8F%91/position-smoothing.svg)

图中仅示意段首、段末速度和加速度均为零的单段运动，此时令 `s=t/T`，有 `q(t)=q0+(q1−q0)(10s³−15s⁴+6s⁵)`；连续运动会使用实际端点速度和加速度。

段长首先由命令周期估计，较大的目标变化会进一步延长执行时间：

```text
T0 = clamp(1.5 P, Tc, 0.2 s)
T  = max(T0, 1.875 × max_i |q1[i] − q0[i]| / vmax)
```

`P` 为估计命令周期，`Tc` 为控制周期，`vmax` 为大于零的插值速度参数；位置与速度须使用相同坐标空间。0.2 s 限制的是时序估计段长，实际 `T` 可以更长。速度和加速度参数用于限制导数估计值及输出值；应用仍需检查完整轨迹的速度、加速度和 jerk。

断流后保留段末位置，输出速度和加速度在 50 ms 内衰减。停稳状态通过设备反馈确认。

手部直接接收最新完整目标，由应用保证目标连续。手部反馈超过 300 ms 无进展时标记过期。停止发送后仍可能继续执行已有目标，停稳状态通过设备反馈确认。

## 关闭与重连

结束时先完成应用的任务停止流程，再关闭订阅及 SDK。`close()` 会取消订阅、清空缓存并释放本对象的对时会话；最后一个对时会话关闭后恢复原系统授时服务状态。重新连接后需要重建用户订阅。Python 可使用 `with NorthSDK(config)` 自动连接并关闭 SDK。

## 故障定位

本节用于应用运行后的数据接收、服务调用和运动准入问题。启动、动态库或导入问题见[首次运行排查](#%E9%A6%96%E6%AC%A1%E8%BF%90%E8%A1%8C%E6%8E%92%E6%9F%A5)，视频依赖和解码问题见[视频环境准备](#%E8%A7%86%E9%A2%91%E7%8E%AF%E5%A2%83%E5%87%86%E5%A4%87)。

| 现象 | 检查 |
| --- | --- |
| 无状态输出或流 silent | 订阅句柄是否仍存活、设备是否安装并在线、机器人侧是否发布数据、连接地址 |
| 缓存读取失败 | 是否收到样本、max_age 是否合理、设备是否持续更新 |
| 调用报错或服务拒绝 | 先检查 SDK 错误，再检查响应的 success/result 和 message，见[错误与结果检查](%E8%BD%AF%E4%BB%B6%E6%9C%8D%E5%8A%A1%E6%8E%A5%E5%8F%A3.md#%E9%94%99%E8%AF%AF%E4%B8%8E%E7%BB%93%E6%9E%9C%E6%A3%80%E6%9F%A5) |
| 运行中设备故障 | 停止发送运动目标，记录故障部位、error_code、fault_codes 和 Master reason。排除急停、掉线等原因后再按设备流程复位；故障持续时将上述信息和软件版本提供给技术支持。 |
| 对时失败或失锁 | 检查机器人有线连接、主机组件和对时诊断，见[时间同步](#%E6%97%B6%E9%97%B4%E5%90%8C%E6%AD%A5)。 |
| 运动被拒绝 | 支持范围、完整目标、command_channel、Master 阶段和模式 |
